Hank’s Tank · the computer science and statistics inside your own code

The algorithms inside your MLB models

Sixteen chapters on how each model you have built actually works: the equations it evaluates, the assumptions it makes, and the code in your repo that implements it. Every parameter shown is the real fitted value from your data, not a textbook placeholder. This is about mechanism, not about how the models scored.

Chapter 01

The shape of the problem

Everything you have built is supervised binary classification. You have a set of games. Each game i has a feature vector xₕ (numbers known before first pitch) and a label yₕ ∈ {0,1} (did the home team win). You want a function that maps features to a probability.

given   (x₁, y₁), (x₂, y₂), …, (xₙ, yₙ)      your 1,763 pregame games
find    f(x) → p ∈ (0,1)                    a probability, not a yes/no
so that p is close to y on games not in the training set

Two details in that framing do a lot of work later. First, the output is a probability, not a class — which is why the loss functions in Chapter 16 score probabilities. Second, “not in the training set” is the whole difficulty: a model can memorise the games it saw, and memorisation looks identical to learning until you test it on new games.

The models differ only in what shape f is allowed to take. A logistic regression makes f a weighted sum pushed through a curve. A tree makes it a nested set of if-statements. A simulator makes it the outcome of playing the game 1,000 times. That is the entire taxonomy.

Chapter 02

Logistic regression

This is V1, and it is also your best-performing model. It computes a weighted sum of the features, then squashes that sum into (0,1).

z  = β₀ + β₁x₁ + β₂x₂ + … + βₖxₖ      the linear predictor, any real number
p  = σ(z) = 1 / (1 + e−z)                the logistic (sigmoid) function

The sigmoid is the only interesting part. It is monotone, so a bigger z always means a bigger probability, and it saturates — near the ends, large changes in z barely move p. That saturation is why a logistic model rarely emits 0.95 unless the evidence is overwhelming.

Inverting it gives the interpretation that matters:

z = log( p / (1 − p) )        the log-odds, or "logit"

So logistic regression is linear in log-odds. A coefficient βₖ is not “how much probability this feature adds” — it is how much the log-odds move per one-unit change in xₖ. Exponentiate it and you get an odds multiplier.

How the coefficients are found

By maximum likelihood. Write the probability of the labels you actually observed, then pick the β that makes it largest. Taking the log turns the product into a sum:

L(β) = Σₕ  yₕ·log pₕ  +  (1 − yₕ)·log(1 − pₕ)     log-likelihood, maximise
ℓ(β) = −L(β) / n                                   log-loss, minimise — same thing

∂ℓ/∂βₖ = (1/n) Σₕ (pₕ − yₕ) · xₕₖ                      the gradient

That gradient is worth staring at. The update for each feature is driven by (prediction − truth) × feature value. When the model is right, the error term is near zero and nothing moves. There is no closed-form solution, so a solver iterates — lbfgs for L2, liblinear for L1.

Chapter 03

Regularisation: L1, L2, and what C actually does

Maximum likelihood alone will happily give a feature a huge coefficient if that helps fit the training data. Regularisation adds a penalty for large coefficients, so the fit has to pay for complexity.

L2 (ridge)   minimise   ℓ(β) + (1/2C) · Σ βₖ²        penalise squared size
L1 (lasso)   minimise   ℓ(β) + (1/C)   · Σ |βₖ|        penalise absolute size

small C  →  strong penalty  →  coefficients pulled toward 0
large C  →  weak penalty    →  approaches plain maximum likelihood

C is inverse regularisation strength. Your models use C=0.1, which is fairly strong — appropriate when you have ~1,300 training rows and the signal is small.

The difference between L1 and L2 is geometric, and it is the reason L1 selects features. Picture the penalty’s constraint region in coefficient space. L2’s is a circle; L1’s is a diamond with corners on the axes. The optimum tends to land where the loss contour first touches that region, and a diamond is far more likely to be touched at a corner — a corner means some coefficients are exactly zero.

Chapter 04

Feature scaling, and why trees do not care

Your elo_differential ranges over hundreds; pythag_differential over tenths. Standardisation puts them on a common scale:

zₖ = (xₖ − μₖ) / σₖ        μ and σ computed on the TRAINING fold only

This matters for two separate reasons. First, the penalty in Chapter 03 is applied to raw coefficient size, so an unscaled feature measured in hundreds gets an artificially tiny coefficient and is effectively over-penalised. Second, gradient descent converges badly when features have wildly different scales, because the loss surface becomes a long narrow valley.

Trees are immune to both. A tree only asks “is xₖ ≤ t?”, and that question is unchanged by any monotone rescaling. This is why V3 onward could throw raw features at XGBoost without a scaler, while your logistic models all need one.

Your scaler

Those are the training-fold means and standard deviations. Fitting them on all the data instead would leak information about the test games into the transform — a small leak, but the same category as the ones that produced the inflated numbers elsewhere in this project.

Chapter 05

Decision trees and boosting

A decision tree partitions feature space into boxes and predicts a constant in each box. It is built greedily: at each node, try every feature and every threshold, and take the split that most reduces the loss.

at each node, choose (feature j, threshold t) maximising
    gain = loss(parent) − [ loss(left child) + loss(right child) ]
recurse until a stopping rule fires (depth, min samples, no positive gain)

One tree is high-variance: change a few rows and the splits move. Boosting fixes that by building many small trees in sequence, each one fitting what the previous ones got wrong.

F₀(x) = a constant                       start with the base rate
for m = 1 … M:
    rₕ = −∂ℓ/∂F(xₕ)                       the "pseudo-residual" — for log-loss, this is (yₕ − pₕ)
    hₘ = a shallow tree fitted to r
    Fₘ(x) = Fₘ₋₁(x) + η · hₘ(x)              η = learning rate, a deliberate under-step
p(x) = σ( F₠(x) )

Each tree is fitted to the gradient of the loss, which for log-loss is just the residual y − p. The trees operate in log-odds space, and the sigmoid is applied once at the end — the same sigmoid as Chapter 02.

The learning rate η is why boosting works: each tree is only allowed to fix a fraction of the remaining error, so hundreds of weak corrections accumulate instead of a few aggressive ones overfitting.

What each XGBoost knob does

The failure mode boosting is prone to

Boosting fits residuals, and in a low-signal problem most of the residual is noise. With enough trees and enough depth, it will fit that noise perfectly. This is exactly what happened in your V8 generation: the model had the capacity to memorise which franchises won at home during 2015–2025, and did.

The defences are all in the table above: shallow trees, a small learning rate, strong reg_lambda, and a large min_child_weight so no leaf is built from a handful of games.

Chapter 06

Bagging versus boosting

Both build many trees, but they attack different halves of the error.

Bagging (RandomForest, ExtraTrees)
    train each tree on a bootstrap sample, on a random feature subset
    predict by averaging — trees are independent, order does not matter
    reduces variance; each tree is deep and overfits, the average cancels it

Boosting (XGBoost, LightGBM, CatBoost)
    train trees sequentially, each on the previous ensemble's residuals
    predict by summing — order is essential
    reduces bias; each tree is shallow and underfits, the sum builds up

ExtraTrees goes further than RandomForest: instead of searching for the best threshold, it picks thresholds at random. That sounds worse and often is not — it adds variance to each tree, which the average removes, and it removes a source of overfitting in the split search itself.

Stacking is the third pattern, and you used it: train several models, then train a small model on their outputs. Your stack fitted a logistic regression on [logit(sim), logit(logit3)]. The key discipline is that the stacker must be fitted on predictions the base models made for games they did not train on, or it learns to trust whichever model memorised hardest.

Chapter 07

Neural networks

Your V9 experiment tried an MLP with layers 128–64–32. An MLP is an alternating stack of affine maps and elementwise nonlinearities.

h₁ = g(W₁x + b₁)        128 units, g = ReLU: g(u) = max(0,u)
h₂ = g(W₂h₁ + b₂)       64 units
h₃ = g(W₃h₂ + b₃)       32 units
p  = σ(wₜh₃ + b)         one output, same sigmoid as Chapter 02

Without the nonlinearity g, the whole stack would collapse: a composition of affine maps is just another affine map, and you would have reinvented logistic regression with extra steps. ReLU is what lets depth buy you anything.

Training is the same idea as Chapter 02 — minimise log-loss by gradient descent — with backpropagation being the chain rule applied efficiently to get the gradient with respect to every weight in every layer.

Why it lost to a 3-feature logistic on your data

Count the parameters. With 121 input features, that MLP has roughly 121×128 + 128×64 + 64×32 + 32 ≈ 26,000 weights, fitted on about 24,000 training games. Roughly one parameter per training example.

Neural networks earn their keep when the input has structure a hand-built feature cannot capture — adjacency in an image, order in a sentence — and when there is far more data than parameters. A table of 121 pre-engineered team statistics has no such hidden structure left to find. This is a case where the model class was a poor match for the data shape, not a case of bad tuning.

Chapter 08

Empirical Bayes shrinkage

This is the statistics inside src/pa_sim/rates.py, and it is the most broadly useful idea in the whole project. The problem: a batter is 4-for-40 in home runs. Is his true rate 10%? Almost certainly not — 40 attempts is nearly no evidence, and 10% would be elite.

The Bayesian answer treats the true rate as drawn from a prior. For a binary outcome the conjugate prior is the Beta distribution, which makes the posterior mean a clean weighted average:

prior      θ ~ Beta(α, β)              with mean α/(α+β) = the league rate
data       x successes in n trials
posterior  θ | x ~ Beta(α + x, β + n − x)

posterior mean  =  (x + α) / (n + α + β)
                =  (x + k·L) / (n + k)        writing k = α+β, L = league rate

Read that last line as a weighted average of the player’s own rate and the league rate, where k is how many games’ worth of league-average evidence the prior is worth. With n small, the league rate dominates. With n » k, the player’s own rate dominates. The shrinkage is automatic and smooth.

The remaining question is where k comes from. Hand-setting it is guessing. Instead method of moments estimates it from the spread of observed rates across all players: if true rates really varied a lot, you would see more spread between players than binomial sampling noise alone can explain, and the excess tells you the prior’s variance.

var(observed rates)  =  var(true rates)  +  E[ binomial sampling noise ]
                                ↓
prior_var  =  var_obs  −  E[ L(1−L)/n ]

k  =  L(1−L) / prior_var  −  1      large k ⇒ players barely differ ⇒ shrink hard
Your fitted shrinkage constants, from 1.7M plate appearances

Every one of these was estimated from your data, not chosen:

The pattern is subtler than “rarer means shrink harder”, and your own numbers show why. What k actually measures is how much of the observed spread between players is real skill rather than sampling noise. Strikeout rate has the smallest batter k (46.7) because K% genuinely varies enormously between hitters. Doubles have one of the largest (1,112) because most of the observed spread is luck.

Triples are the interesting case: they are far rarer than doubles, yet their batter k is lower (638 vs 1,112). The formula has discovered that triple rate reflects a real, persistent skill — footspeed — so it shrinks them less than their rarity alone would suggest. Compare the pitcher column, where triples have the largest k of all (2,488): a pitcher has almost no control over whether a ball becomes a triple. The same statistic, split by role, correctly identifies that this is a batter skill and not a pitcher skill. Nobody told it that.

A sign error worth remembering

When splitting rates by pitcher handedness, the split samples are about half the size, so they need to be shrunk harder — a larger k. The first version of this code multiplied k by 0.5, which shrinks less, letting a 120-PA vs-lefties sample move the estimate more than the player’s full-season sample could. Fixing it to k × 3.0 changed the model from failing its validation gate to passing it. The direction of a shrinkage adjustment is easy to invert and the code still runs.

Chapter 09

Odds ratios and log5

Given a batter who homers 5% of the time and a pitcher who allows 2% against a league rate of 3%, what happens when they meet? Averaging is wrong — it ignores that both numbers are already measured against the same league.

The right move is to work in odds, where the effects multiply:

odds(p) = p / (1 − p)

odds(matchup)  =  odds(batter) × odds(pitcher) / odds(league)

p(matchup)     =  odds / (1 + odds)          convert back

Dividing by the league odds is the important part: it removes the league baseline that is already baked into both individual rates, so you are combining the two deviations rather than double-counting the average. This is the classic log5 formula, and it has a neat property — a league-average batter against a league-average pitcher returns exactly the league rate.

For an outcome with more than two possibilities, the same idea extends multiplicatively and then renormalises:

rawₘ  =  bₘ · pₘ / Lₘ              for each of your 8 outcome classes
Pₘ    =  rawₘ / Σₕ rawₕ            renormalise to a valid distribution
In your code

src/pa_sim/rates.py → log5() implements exactly this over the eight classes K, BB, 1B, 2B, 3B, HR, OUT, DP. The unit test test_log5_is_neutral_at_league_average checks the neutrality property, and test_log5_moves_the_right_way checks that a high-strikeout pitcher raises the strikeout probability. Both tests encode a mathematical property rather than a remembered output, which is the kind of test that survives refactoring.

Chapter 10

Markov chains

A Markov chain is a system that moves between states, where the next state depends only on the current one — not on how you got there. That property is the Markov assumption, and baseball satisfies it well: given runners on first and second with one out, how the inning reached that configuration barely matters.

Your state space is small and exact:

bases ∈ {000, 100, 010, 001, 110, 101, 011, 111}     8 occupancy patterns (3 bits)
outs  ∈ {0, 1, 2}                                   3 values
                    8 × 3 = 24 states, plus an absorbing "3 outs"

Each plate-appearance outcome is a deterministic transition from a state, producing a new state plus some runs. Because there are only 8 outcome classes and 24 states, the whole thing is a fixed 24×8 lookup table — built once in src/pa_sim/markov.py.

Once you have the table, you can compute the exact distribution of runs in an inning without simulating anything. Maintain a probability distribution over (state, runs-so-far) and push it through one plate appearance at a time:

for each PA t:
    for each live (bases, outs, runs) with probability w:
        for each outcome e with probability Pₘ:
            move w·Pₘ into (new_bases, new_outs, runs + runs_scored)
            or into the "inning over" accumulator if it made the 3rd out

This is dynamic programming: the answer is built from the answers to smaller subproblems, and no sampling is involved. The result is the true run distribution to floating-point precision.

Where the Markov assumption is genuinely wrong here

Your table advances runners deterministically — a single always moves a runner exactly one base. Real baseball is probabilistic: a runner scores from second on a single roughly 60% of the time depending on the runner, the outfielder, and the number of outs. That is a modelling choice, and it narrows the run distribution slightly. It was compensated for with a single global scaling factor rather than fixed properly, which is a known limitation of the implementation rather than of the method.

Chapter 11

Monte Carlo

If the chain in Chapter 10 gives the exact answer, why also sample it 1,000 times? Because exactness stops being available as soon as the model gets realistic. Walk-off rules, the home team skipping the bottom of the 9th when ahead, extra innings, a pitcher change mid-inning — each of these breaks the clean recursion. Sampling does not care.

Monte Carlo replaces “compute the distribution” with “draw from it many times and count”. Its accuracy is governed by one formula:

estimate  μ̂ = (1/N) Σ Xᵢ                    the sample mean of N episodes
error     SE = σ / √N                       standard error

⇒  4× the episodes buys 2× the precision.  Halving the error costs 4× the compute.

That square root is why 1,000 episodes is a reasonable default and 100,000 is rarely worth it. It also sets the floor on what a simulator can resolve: with N=1,000, a win probability has a standard error of about √(0.25/1000) ≈ 1.6 percentage points. Any “edge” smaller than that is invisible to the simulation itself.

The verification trick worth stealing

You have two independent implementations of the same process: the exact recursion and the sampler. They must agree, and how closely is predictable from the formula above. Measured on your code:

Agreement to 0.17 standard errors at 100,000 episodes. Neither implementation validates itself, but the two together do — a bug in the transition table would break both identically, while a bug in either the recursion or the sampling loop shows up as a divergence. This is the strongest correctness evidence available when you have no ground truth to compare against.

Chapter 12

Poisson and Skellam

Instead of predicting who wins, you can predict how many runs each side scores and derive the winner. Runs are non-negative integers, so the natural first model is Poisson.

P(X = k)  =  λk e−λ / k!             X = runs, λ = expected runs
E[X] = λ      Var[X] = λ                mean and variance are the SAME number

log λ  =  β₀ + β₁x₁ + …                  Poisson regression: model log λ linearly

The log link is what keeps λ positive for any coefficients. Note the mean-equals-variance property — it is a strong assumption, and baseball violates it. Real run distributions are overdispersed: variance exceeds the mean, because innings are correlated and a blowout is a single cascading event. A negative binomial adds a dispersion parameter to fix this, and is the natural next step if you revisit this.

Given two independent Poisson counts, the distribution of their difference has a name:

Xₕ ~ Poisson(λₕ),  Xₖ ~ Poisson(λₖ)
Xₕ − Xₖ ~ Skellam(λₕ, λₖ)

P(home wins) = P(Xₕ − Xₖ > 0) = 1 − Skellam_cdf(0; λₕ, λₖ)

This gives a closed-form win probability from two run models, with no simulation at all — scipy.stats.skellam in research/backtest_2026/19_score_target.py. The tie mass needs handling separately, since baseball has no ties.

Why modelling runs is theoretically attractive

A win/loss label carries one bit. A final score carries much more — a 9–2 result and a 3–2 result are both “home win” but say very different things about the teams. Training on the score therefore extracts more information per game from the same schedule. That is a real and standard argument, and it is why this is worth understanding even though on your data the approach did not end up winning.

Chapter 13

From Elo to Kalman filters

Elo is probably the most familiar algorithm in your stack, and seeing what it really is unlocks a large family of methods. Elo is an online update rule:

predict   p = 1 / (1 + 10−(Rₕ−Rₖ)/400)      a sigmoid on the rating difference
update    Rₕ ← Rₕ + K·(outcome − p)           move toward the surprise

Look at the update: (observed − predicted) × a constant. That is the same shape as the logistic-regression gradient in Chapter 02, applied one game at a time. Elo is stochastic gradient descent on a two-parameter logistic model with a fixed step size.

And that fixed step size is its weakness. K is the same for a team you have watched for 800 games and a team fresh out of the offseason, even though your uncertainty about them is wildly different. What you want is a step size that depends on how well the rating is currently known. That is a Kalman filter.

state       θₜ = φ·θₜ₋₁ + ηₜ          η ~ N(0, Q)     latent strength, drifts over time
observation yₜ = θₕ − θₖ + h + εₜ      ε ~ N(0, R)     run margin, noisily observed

predict     P ← φ²P + Q                              uncertainty grows between games
innovation  v = y − (θₕ − θₖ + h)                     the surprise
gain        K = PHᵀ / (HPHᵀ + R)                       DERIVED, not chosen
update      θ ← θ + K·v ,   P ← P − K·HᵀP                shrink uncertainty

Two things are worth unpacking. P is a full covariance matrix over all 30 teams, so beating a team you were uncertain about updates your belief about that team more, and correlations between teams are tracked. And the gain K is a ratio of how uncertain you are to how noisy the observation is — when P is large relative to R, trust the new game; when P is small, trust your existing estimate.

What your fitted parameters revealed

Tuning on 2015–2019 chose q = 0.0008, φ = 1.0, season_inflate = 1.0. Read those: φ = 1.0 means no mean reversion — a pure random walk. season_inflate = 1.0 means no extra offseason drift. The data asked for the simplest possible version of the model and declined the extra machinery.

That is a genuinely useful outcome. A fitted parameter sitting exactly at the boundary of its range is the model telling you that term is not needed. src/edge/statespace.py

Chapter 14

Calibration

A model can rank games perfectly and still print wrong numbers. Discrimination (does it order games correctly) and calibration (do the stated probabilities match reality) are independent properties, and they need separate fixes.

The standard test is a reliability curve: bucket predictions, then compare mean predicted against observed frequency in each bucket. The two standard repairs:

Platt scaling — fit a 1-D logistic regression on the model's own logit
    p′ = σ( a·logit(p) + b )
    2 parameters, monotone, cannot reorder anything, works on small data

Isotonic regression — fit the best non-decreasing step function
    p′ = g(p),   g monotone, fitted by pool-adjacent-violators
    non-parametric, more flexible, needs more data or it overfits the steps

Both are monotone, which is the key property: they change the numbers without changing the ordering, so AUC is untouched while log-loss and Brier improve. Your project also used a third, simpler form — shrinking toward the base rate:

p′ = base + λ·(p − base)        λ = 0.38 fitted on your data
The subtlety that caught this project

Shrinking toward the base rate is monotone for a fixed base and λ. But when both are refitted weekly, the transform differs between weeks, so the global ordering does change — and predictions near 0.5 can cross the decision boundary. That is how a “calibration fix” ended up changing 164 actual picks.

If you want calibration without changing picks, fit one transform and keep it fixed, or define your confidence tiers as quantiles of the prediction distribution rather than absolute thresholds. Quantile tiers are invariant to any monotone recalibration.

Chapter 15

Hyperparameter search

Model parameters are learned from data; hyperparameters (tree depth, C, learning rate) are chosen by search. There are three generations of method, and your project used all three.

Grid search     every combination on a lattice
                 cost explodes as dᵗ; wastes trials on dimensions that do not matter

Random search   sample uniformly from the space
                 provably better than grid in high dimensions, because most
                 hyperparameters are irrelevant and random search never wastes
                 a whole axis resolving one of them

TPE (Optuna)   model-based: build p(good) and p(bad) over the space from
                 completed trials, then propose points maximising p(good)/p(bad)

TPE is “Tree-structured Parzen Estimator”. Rather than modelling score = f(params) directly as a Gaussian process would, it splits past trials into good and bad by a quantile, fits a density over each group, and samples where the ratio is highest. This handles conditional spaces naturally — max_depth only exists when the family is a tree — which is why it suits a search over several model families at once.

Reading a search as a diagnostic, not just a chooser

Your 300-trial run spent 265 trials on the 3-feature configuration. That concentration is not just how TPE finds an optimum — it is information. A sampler piling up in one corner of the space is telling you that region dominates, and a sampler that spreads evenly is telling you nothing distinguishes the options.

The essential discipline: the search must be scored by walk-forward validation inside the search set, with any feature selection performed inside each fold. Selecting features on all the data and then cross-validating measures a model that has already seen the answer.

Chapter 16

Loss functions, and what “proper” means

A scoring rule is proper if it is optimised by reporting your true belief. This is a mathematical property, not a preference, and it is why accuracy is a poor training target.

Log-loss   ℓ = −[ y·log p + (1−y)·log(1−p) ]
             proper · unbounded · punishes confident errors severely
             log(0) = −∞, so one confident mistake can dominate

Brier      ℓ = (p − y)²
             proper · bounded in [0,1] · gentler on confident errors

Accuracy   ℓ = 1 if (p ≥ 0.5) ≠ y
             NOT proper · discards the probability · zero gradient almost everywhere

Here is why properness matters concretely. Suppose your honest belief is 60%. Under log-loss, your expected score is best if you report exactly 0.60. Under accuracy, reporting 0.60 and reporting 0.99 score identically — both land on the same side of 0.5. Accuracy gives you no reason to be honest about magnitude, and no gradient to learn from, which is why every model here trains on log-loss and is only reported in accuracy.

The decomposition below is the reason both properties from Chapter 14 show up in one number:

Brier  =  reliability  −  resolution  +  uncertainty
          (calibration)    (discrimination)   (irreducible)

A proper score improves if you calibrate better or discriminate better, and the third term is the floor set by the problem itself. Two models with identical Brier scores can be differently broken — one badly calibrated but sharp, the other honest but vague — which is exactly why you look at reliability curves alongside the aggregate number.
