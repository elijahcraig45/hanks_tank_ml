02 · Why it was worth building

A different substrate, not a different model

Every previous attempt predicted a binary label from season aggregates: roughly 1,300 usable games a year, which is about 1,300 bits of training signal. Five distinct mechanisms and 450 search trials all failed to beat a 3-feature logistic on it. The simulator trains on something else entirely.

03 · Backtest

Five gates, four passed

Each phase validates on a target with far more statistical power than the final one, so components could be proven or killed before reaching the underpowered win/loss target.

04 · Head to head

Both windows, same games

A candidate has to win in the search window and the untouched holdout. On this dataset a single-window improvement has been wrong every time it has been checked, so the gate is deliberately strict.

05 · Production status

What is shipped, and what is deliberately not

The simulator is production-wired and can run on the live schedule today. It writes mlb_2026_season.game_predictions_sim — a shadow table — and never game_predictions. Deploying it therefore cannot change what hankstank.com serves, and both models get scored on the same games.

Not done, on purpose

Nothing has been deployed. deploy_pa_sim.sh has only been run with --dry-run; the shadow table does not exist yet; no Scheduler job was created. Pushing a model to the live Cloud Function is a production change and is yours to make.

A cold start fetches ~2M PAs from BigQuery in about 100 s. That fits the 540 s function budget but is a real share of it — the /tmp cache covers warm invocations, and a GCS-backed rate artifact would remove it entirely.

06 · Recommendation

The honest read

The build worked. The premise held at every level where it could be measured with real power: the PA model carries genuine matchup signal on 183,000 held-out plate appearances, the run generator reproduces actual run totals with a −0.09 run bias and monotone quintiles, and the Monte Carlo engine agrees with exact analytic math to a fifth of a standard error.

What did not happen is the part that matters: the extra information does not survive aggregation into a single win/loss. A game is roughly 76 plate appearances of accumulated noise, and the edge that is clearly visible at PA level is worth about a point of accuracy by the time it becomes one bit. The simulator beats V10 — but so does a logistic regression on three columns, by more, in both windows.

So: run it in shadow mode, do not promote it. Shadow costs almost nothing, scores both models on the same games, and gives a clean read on fresh 2027 data where the rates will not be stale. Promote only if it clears the 3-feature baseline in both windows on that fresh data.

And the thing this exercise keeps pointing at remains true: the simulator is a better mechanism fed the same public information. Market odds are different information — injuries, weather, lineup scratches, sharp money — and they are still both the ~58–60% benchmark and the most valuable single feature not yet in the stack.
